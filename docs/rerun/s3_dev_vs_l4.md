# S3：在 RTX 6000 Ada 上重采 14 篇 dev，与已提交的 L4 汇总结果对比

## 做了什么
- 采集：`python -m collect.long --split splits/longctx_v1.json --subset dev --out data/dev --dense-reference`，wulab2 卡 0（UUID `GPU-a74391df-5c27-152f-d0c0-6b86f8ea07d3`），2026-11-25 06:44–06:56 UTC，每篇 14–30 s（另有同样长度的 dense 参考生成）。
- 13 篇以 EOS 结束，1 篇（qmsum/975d…，724 步）按 32-gram 重复规则停止（498–950 步，共 10 775 步；L4 是 473–1016 步，共 10 913 步）。`heldout.check_traces(..., "dev", 28)` 通过，每篇写完立即用严格读取器 `kvpolicy.load` 校验。原始 trace 共 653 MB，放在 wulab2 的 `data/dev/`，sha256 写在每篇的 manifest 里。
- 回放：原样运行 `efficient_dev.py` 和 `checks.py`（输出 `results_v2/dev/efficient_dev/`），与 `docs/results/longctx_dev/summary.csv`（L4）对比。对比脚本是 `analysis_v2/compare_l4.py`。

## 结论
1. **汇总数字几乎不变。** B=96 时 LRU miss 率 6.04 %（L4 6.03 %），Bélády 3.87 %（3.86 %），分数 EMA（LODO）G = 0.279 [0.274, 0.283]（L4 0.279 [0.274, 0.284]）。当前分数 0.240（0.244），线性 DAgger 0.300（0.300），按层分配 + hybrid 0.373（0.381）。
2. **单篇文档的生成长度变了很多**（例如 gov_report/0708… 从 613 步变成 950 步，gov_report/8ea6… 从 873 步变成 594 步），说明换 GPU 后选择和生成本来就不同（STATUS_REPORT 已记录 A100 和 L4 之间也是这样）。但按文档和层汇总后的比例很稳定。
3. 下表 68 行（策略 × 5 个预算）中，新 G 有 13 行落在 L4 的 bootstrap CI 之外：arc 在 B=72、80、128；rank(lodo) 在 B=72、128、256；score 在 B=72；alloc+best_hybrid 和 alloc+lru 在 B=128（0.484 对 0.506，0.289 对 0.310，两组 CI 重叠）；lru2 在 B=128；linear-bc/dagger 在 B=256（0.334 对 0.317）。这些差别都不超过 0.022。唯一较大的是 lfu 在 B=256（−0.898 对 −1.014），LFU 本身在各文档之间波动很大（CI 宽 0.25）。CI 只反映文档重采样的方差，不包括 trace 本身的变化，所以 CI 外的小差异在预期之内。分数类策略之间的排序（linear > EMA > score ≈ hybrid > rank ≈ LRU）在每个预算上都和 L4 相同。
4. 没有程序错误的迹象：每层 miss 率都大于 0，每个（文档，层，预算）上 Bélády ≤ LRU（`results_v2/dev/audit.txt`），步数正常。
